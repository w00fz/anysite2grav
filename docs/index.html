What you get

Your site in Grav, ready for your agent

Not a static scrape. You get a real Grav site that you and your agent can edit: content in pages and frontmatter, design in an editable theme, and every setting in Admin.

Same URLs, same content

One Grav page per source URL, with the exact title, meta and Open Graph tags. Long pages become modular pages with one editable module per section; short ones stay single pages. Markdown for articles, deduplicated media, redirects kept.

A theme that looks the same

A standalone theme built from the source's measured styles and its own CSS rules. Header, menus, CTAs and footer are editable in Admin. Tailwind 4 if you want it.

Forms that actually work

Every form, including the ones in popups, becomes a Grav form that submits in place. Grav's built-in Cap CAPTCHA needs no keys. Submissions are saved, emailed or sent to a webhook, as you choose.

Your agent can edit it from the start

Admin2, the REST API and the Grav MCP server are set up before any content work. The MCP launcher reads the key itself, so no secret ends up in your agent's config.

Analytics ported, firing on production hosts only Local and preview copies kept out of search with noindex Native multilang or per-language trees PHP server or Docker with Mailpit DESIGN.md recording every styling decision
How it works

Thirteen checkpoints in six stages

The agent works through a fixed checklist. Each checkpoint has a check that must pass before the next starts, and every script is safe to rerun, so a better extraction rule can rebuild the site without losing your hand-made changes.

STAGE 01

Set up

1 Intake2 Install3 API + MCP
  • Confirms the URL, project folder, runtime (PHP's built-in server, Docker or your own stack) and which agents to connect.
  • Installs the latest Grav 2 with Admin2 in a new folder and starts it.
  • Creates an admin account and an API key, writes an MCP launcher and .mcp.json, and registers it with Claude Code, Codex or Cursor. Credentials stay in .local/ with 0600 permissions.
Check: you can sign in to /admin and your agent can call list_pages.
STAGE 02

Discover

4 Routes5 Audit
  • Reads robots.txt and every sitemap, then crawls the site, because many site builders publish no sitemap or an incomplete one.
  • Detects fake 404s that return 200, redirect chains, hreflang languages and linked PDFs, including those hosted on a CDN.
  • Audits the site: every tracker with its ID (GTM, GA4, Meta, HubSpot, Hotjar, Heap…), every form and where it appears, embeds, inline custom code, fonts and the color palette.
Check: you review the route list and audit.md before anything is built.
STAGE 03

Decide

6 Questions
  • Once the audit is done, it asks the questions only you can answer together, each with a recommended default: theme name and styling, language handling, each form's delivery and CAPTCHA, and analytics.
  • Your answers, and the options you turned down, go into the project notes because later stages depend on them.
Check: nothing styling-related happens until Tailwind or plain CSS is settled.
STAGE 04

Rebuild

7 Extract8 Pages9 Theme10 Forms11 Analytics
  • Extracts every text block, including text builders put in bare divs and spans, plus card grids, galleries, background videos and popups. Splits out the header, footer and sections repeated across pages.
  • Downloads each media file once, deduplicated by SHA-256, and stores it with its page or in shared site media.
  • Builds the page tree with frontmatter, blueprints, source provenance, shared sections and redirects. Every YAML file is linted with Grav's own parser.
  • Splits long pages into modules. More than three horizontal sections makes a modular page, one module per section. Three or fewer stay a single page.
  • Scaffolds the theme from the source's measured colors and type, and copies its section and card CSS onto .src-* hooks. That one step carries most of the look over.
  • Converts the forms into /forms/<name> pages embedded wherever the source showed them, and adds analytics if you chose to.
Check: the YAML lint is clean, every route returns 200, and each form is submitted in a real browser.
STAGE 05

Match

12 Fidelity loop
  • Works through groups of pages that share a layout, largest first. Takes source and local screenshots side by side at 1440px and 390px with Playwright.
  • --metrics lists each section's height, padding, background and heading type for both sites, so fixes come from measurements, not guesswork.
  • Promotes layouts that need editor-friendly fields into their own page types, with a template and a blueprint.
  • A route-by-route verifier checks titles, text coverage, images, forms, leftover CDN assets, lang/hreflang, noindex and analytics leaks.
Check: every route passes the verifier and you approve the side-by-side report.
STAGE 06

Hand off

13 Finish
  • A final round: the verifier, the YAML lint, a clean Grav log, and one field edited through Admin or MCP that shows up on the rendered page.
  • Optionally runs git init in grav/user, with accounts, submissions, API keys and caches ignored.
  • A handoff summary: URLs, where credentials live, the MCP connection, your decisions, parity numbers and what still needs you, such as SMTP or font licenses.
Page structure

One page or modular, decided per page

The rule of thumb: more than three distinct horizontal sections means a modular page. Anything shorter stays one page with its sections in frontmatter. The skill counts what a visitor scrolls through (popups don't count) and builds each page the right way.

≤ 3 sections

Single page

03.pricing/
└── sections.en.md   # title, meta, sections: [ … ]

One file and one Admin form. Editing a short page is quickest when everything is in one place.

4+ sections

Modular page

01.home/
├── modular.en.md          # title, meta, popups
├── 01._hero/hero.en.md
├── 02._why-teams-switch/cards.en.md
├── 03._partners/gallery.en.md
├── 04._newsletter/shared.en.md
└── 05._contact/form.en.md

Each section becomes a module with its own Admin form and media folder. Reorder, hide or edit one section without touching the rest.

hero first section with an H1 or a background cards feature and card grids gallery logo strips and photo sets form sections with a form shared a section reused site-wide section everything else

Every module kind has its own template and Admin form, so you can give, say, all heroes named fields later. Change the cut-off with --modular-threshold, or turn modules off with --modular off.

What ends up on disk

One folder for everything

Grav, the migration files and the agent wiring sit side by side, and only grav/user needs to be in git.

~/Sites/acme-grav/
├── grav/              # Grav 2 + Admin2, API, Form, Email
│   └── user/          # the site: pages, config, theme
│       ├── pages/     # one folder per source URL
│       │   ├── 01.home/   # modular: one module per section
│       │   │   ├── modular.md
│       │   │   ├── 01._hero/
│       │   │   └── 02._features/
│       │   └── 02.pricing/ # 3 sections or fewer
│       ├── themes/acme/
│       └── media/     # shared images + PDFs
├── migration/         # crawl, audit, reports, screenshots
│   ├── routes.json
│   ├── audit.md
│   ├── parity-report.md
│   ├── screens/       # source vs local, side by side
│   └── fixups/        # your rerunnable custom changes
├── .local/            # credentials (0600, never committed)
├── bin/grav-mcp       # MCP launcher, reads the key at start
└── .mcp.json          # Claude Code picks it up
01

Scripts write the bulk, MCP handles later edits. The page tree is written to disk in one fast, repeatable pass. After that you and your agent edit through Admin or MCP, which handle concurrent edits safely.

02

Rerun anything. Every script is idempotent. Your own page types and fixes go in migration/fixups/ as scripts, so rebuilding never loses them.

03

Generic first, custom when it pays off. Pages and modules start as editable blocks. A module kind (every hero, say) or a layout used across many pages can be promoted to named Admin fields.

04

Nothing secret leaks. No key or password is printed, logged or committed. SMTP passwords go in environment variables, not YAML.

Install

Add it to your agent

It follows the open Agent Skills format: a SKILL.md with scripts and references loaded only when needed. One folder works in Claude Code, Codex and any other agent that reads skills.

Add the marketplace, then install the plugin. Run these inside Claude Code:

/plugin marketplace add w00fz/grav-skills
/plugin install website-to-grav@grav-skills

Updates come through /plugin marketplace update grav-skills.

Clone the repo and link the skill into your personal skills folder:

git clone https://github.com/w00fz/grav-skills.git ~/Projects/grav-skills
ln -s ~/Projects/grav-skills/skills/website-to-grav ~/.claude/skills/website-to-grav

A git pull updates it.

Link the same folder into Codex's skills directory:

git clone https://github.com/w00fz/grav-skills.git ~/Projects/grav-skills
ln -s ~/Projects/grav-skills/skills/website-to-grav ~/.codex/skills/website-to-grav

Codex shows it as Website to Grav. Call it with $website-to-grav.

Any agent that supports Agent Skills can load skills/website-to-grav/ directly. Agents without skill support can be pointed at SKILL.md: it's a plain checklist with every command it runs.

skills/website-to-grav/
  SKILL.md         # the workflow, decisions and rules
  references/      # read only when a step needs them
  scripts/         # crawl, audit, extract, build, verify…
  assets/          # theme skeleton + Docker runtime

Private repo: installing needs read access to w00fz/grav-skills. Claude Code and git use your existing GitHub login.

Under the hood

Plain scripts, no framework

The agent makes the judgment calls; scripts do the repetitive work and give the same result every time. Python uses only the standard library, PHP calls Grav's own YAML parser, and Node runs only when screenshots or Tailwind need it. Every script has --help.

install_grav.sh

Latest grav-admin into the project, with PHP and extension checks.

bootstrap_access.sh

Admin user, API key, MCP launcher and .mcp.json. Safe to rerun; --rotate-key issues a new key.

crawl_site.py

Sitemaps plus a crawl, giving the route list, cached HTML, redirects, languages and PDFs.

audit_site.py

Trackers, forms, embeds, inline code, fonts and palette, written to audit.md.

extract_content.py

Sections and blocks, menus and footer, shared sections and layout groups.

import_media.py

Downloads each file once, deduplicates by SHA-256 and decides where it's stored.

build_pages.py

Page tree with modular pages for long layouts, frontmatter, languages, redirects and a map of every page.

scaffold_theme.py

Theme from the skeleton, the measured design tokens and the ported source CSS, with optional Tailwind.

build_forms.py

A form plan for your answers, then the Grav Form pages and CAPTCHA config.

capture_pages.mjs

Playwright screenshots of source and local, plus computed tokens and per-section measurements.

verify_parity.py

A route-by-route parity report covering status, titles, coverage, media, forms, SEO and analytics.

grav_config.php

Merges, reads and lints YAML with the same parser Grav uses.

Learned the hard way

Rules the skill always follows

The skill comes from a real Webflow-to-Grav migration. Each rule below is there because breaking it caused a problem in that migration.

  • Every source URL survives. Nothing gets renamed without a 301 redirect, and it asks before "cleaning up" ugly builder slugs.
  • Analytics never fire off production. Local and preview hosts load no trackers.
  • Preview copies stay out of search through a noindex meta tag and X-Robots-Tag, not a robots.txt block that would stop crawlers seeing the noindex.
  • No fake integrations. A form stores or sends what it collects, and its success message says which.
  • Secrets are never printed, logged or committed. Agent configs point to a launcher instead of holding the key.
  • Admin, API and MCP are for authoring. The production profile doesn't expose them.
  • Grav's built-ins first: Form and Cap, Email, page media, media:// and native multilang, before any custom code.
  • The theme's JavaScript has no dependencies. Menus, popups and the language switcher are written by hand, so jQuery is never needed.
